# Supabase — основа блока 05

Дата: 2026-11-24. **Статус: blocked — внешний Supabase ещё не подключён.**
Миграции проверены на изолированном PostgreSQL PGlite; это не подтверждение
работы hosted Supabase, Auth, Storage API или полноценного оформления заказа.

## Что требуется владельцу

1. Открыть [Supabase Dashboard](https://supabase.com/dashboard), войти в свой
   аккаунт и создать **отдельный бесплатный** проект `kos-jeans-dev`.
   Production-проект и рабочие данные не использовать. Пароль БД сохранить
   в менеджере паролей; в Git и чат его не отправлять.
2. В Connect / API Keys скопировать Project URL и **Publishable key**
   (`sb_publishable_…`). Создать в корне локальный `.env.local` по `.env.example`:

   ```dotenv
   NEXT_PUBLIC_SUPABASE_URL=<Project URL тестового проекта>
   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<Publishable key тестового проекта>
   ```

   Это шаблон, значения в угловых скобках нужно заменить. `.env.local` игнорируется
   Git. Настоящие значения не вставлять в README, PR, скриншоты или команды чата.
3. Сообщить, что тестовый проект создан и файл заполнен. Для применения миграций
   нужна также авторизация CLI: выполнить в своём терминале из папки проекта
   `npx --yes supabase@3.3.0 login` и завершить вход самостоятельно.
   Publishable key позволяет работать с API через RLS, но **не даёт права DDL**.
4. В Auth → настройки регистрации отключить публичную регистрацию в тестовом
   проекте. Создание тестовых пользователей и назначение роли выполнить отдельно
   через доверенный интерфейс владельца после применения миграций.

Ни CLI-авторизация, ни создание внешнего проекта в этой сессии не выполнены.
`supabase whoami` вернул AccessTokenRequiredError. Docker/psql также отсутствуют.

## Применение миграций после авторизации

CLI 3.3.0 использует явный `--remote`. Эти команды пока **не выполнялись**:

```bash
npx --yes supabase@3.3.0 link --project-ref <ref-тестового-проекта>
npx --yes supabase@3.3.0 db push --remote --dry-run --skip-vault
# Сверить ref и список: только две миграции из этого репозитория.
npx --yes supabase@3.3.0 db push --remote --skip-vault
npm run db:check
```

Пароль, если его запросит CLI, вводить в скрытый интерактивный prompt,
не передавать аргументом `--password`. Команды изменения БД направлять только
в согласованный dev-проект. Без `--include-seed`: тестовые данные не публикуются
автоматически. CLI ведёт историю применённых миграций.

Первая миграция создаёт схему и RLS, вторая — bucket/Storage policies. Каждая
обёрнута в транзакцию; существующие таблицы/bucket с теми же именами вызовут
ошибку, а не будут перезаписаны. Не пытаться повторно выполнять миграцию
после успешной записи истории. Изменения production-БД требуют отдельного разрешения.

Ручной SQL Editor доступен как запасной способ, но требует отдельно согласовать
историю миграций с CLI; не смешивать оба способа без `migration repair`.
`tests/helpers/supabase-platform.sql` предназначен **только для PGlite**, его
категорически нельзя запускать в Supabase.

## Схема

| Таблица | Назначение и ограничения |
| --- | --- |
| categories | UUID, parent_id, уникальный изменяемый slug, sort_order, видимость, архив; FK restrict и защита от циклов |
| products | UUID, уникальные slug/SKU, описание/материал/JSON-характеристики, draft/published/archived, даты, new/featured |
| product_categories | Many-to-many, составной PK, индексы обоих направлений; категория с товарами не удаляется |
| product_images | Путь в bucket, alt, порядок, одна главная фотография на товар |
| product_variants | Собственный SKU, произвольные размер/цвет, уникальное сочетание на товар, активность, отдельный stock ≥ 0 |
| orders | UUID, номер, уникальный idempotency_key, fingerprint, снимок контактов/доставки, статус, сумма, маркер возврата остатков |
| order_items | Снимки имени/SKU/размера/цвета/цены; quantity, сумма строки, FK заказа и согласованной пары variant/product |
| store_settings | Только публичный контент известных ключей; поле is_public; никаких секретов |
| homepage_banners | Иллюстрация/alt, локальная ссылка, сортировка, видимость и окно публикации |
| private.admin_users | UUID пользователя Auth; закрытая таблица ролей с RLS, без клиентских grants |

Деньги — целые копейки: `integer` для цены единицы, `bigint` для итогов,
UAH фиксирована. Итоги ограничены безопасным диапазоном JS integer. Скидка
требует старую цену выше новой. Строка заказа проверяет `цена × количество`.
Цена/название в снимке не меняются при обновлении товара; удаление товара/варианта
обнуляет ссылки, сохраняя снимок. Заказы с позициями не удаляются каскадом.

Фактическая связь общей суммы заказа с суммой всех строк, создание снимков,
лимиты HTTP и отмена заказа будут реализованы в единой доверенной операции
блока 12/13. Сейчас никто из anon/authenticated, включая администратора,
не может записывать orders/order_items напрямую.

## Доступ и роли

Публичное чтение: видимая неархивная категория **со всеми видимыми предками**;
опубликованный товар с наступившей датой публикации хотя бы в одной такой
категории; активные варианты и связанные фото; разрешённые настройки и баннеры.
Draft, archived, будущие публикации, скрытые категории/предки не раскрываются.

Обычный authenticated имеет те же публичные чтения и не видит заказы.
Администратор читает закрытый каталог и заказы, управляет каталогом/контентом/
фотографиями. Записи заказов пока закрыты всем клиентским ролям.

`private.is_admin()` — SECURITY DEFINER с пустым search_path, проверяет только
`auth.uid()` в закрытой таблице, не доверяет user_metadata. `public.is_store_admin()`
возвращает лишь роль текущего authenticated пользователя для будущей серверной
проверки; не назначает роли. Схему private не добавлять в Exposed schemas.

Первого администратора назначает только владелец БД после проверки UUID
реального пользователя в Auth. Пример, **не выполнен**:

```sql
insert into private.admin_users(user_id) values ('<проверенный UUID из Auth>');
```

Нет автоматического назначения первому зарегистрировавшемуся и демопароля.
Отзыв роли — удаление доверенным владельцем строки private.admin_users.

## Серверный и браузерный клиенты

- `src/lib/supabase/client.ts` — браузерный createBrowserClient.
- `server.ts` — новый серверный клиент на запрос, cookies, `server-only`.
- `session.ts` — подготовленный refreshSession для Auth proxy блока 08;
  сейчас не подключён к storefront. До auth-маршрутов его нужно включить
  в соответствующий proxy и проверить обновление/отзыв сессии.
- `config.ts` — явная ошибка при отсутствии env или попытке использовать
  sb_secret_/legacy service-role вместо publishable key.

Оба клиента используют publishable key и сессию пользователя, сохраняют RLS.
Привилегированного runtime-клиента нет. Главная не вызывает Supabase и работает
без env. Реальный каталог, login, admin UI и заказы в этом блоке не добавлены.
Типы Database нужно генерировать из применённой схемы перед блоком 06.

## Storage

`store-media`: **private**, максимум 5 МиБ на файл, JPEG/PNG/WebP; SVG запрещён.
Пути: `products/<UUID>/<file-id>.webp`, `categories/<UUID>/<file-id>.jpg`,
`banners/<UUID>/<file-id>.png` (также jpeg). Родитель должен существовать.

Upload/update/delete разрешены только администратору. Публичное чтение — лишь
файлы, привязанные к публичному товару/категории/активному баннеру. Draft-файлы
и ещё не привязанные загрузки доступны только администратору. Raw public URL
для этого bucket не используется. В будущем фронтенд получает короткие signed
URL через RLS-клиент или защищённую серверную выдачу; уже выданная signed-ссылка
остаётся действительной до своего TTL, поэтому рекомендуется 60 секунд.

Bucket-параметры MIME/размера проверяет Storage API; SQL RLS проверяет роль/путь/
связи/видимость. Админка позднее дополнительно проверит содержимое и размеры
изображения, создаст UUID-имя и безопасно обработает незавершённую загрузку.
SQL-таблицы storage.objects напрямую для загрузки/удаления не изменять.

## Тесты и границы результата

`npm test`: 17 тестов (14 БД/RLS/Storage SQL, 2 цены, 1 конфигурация).
Каждый запуск создаёт новый PostgreSQL PGlite в памяти, применяет обе миграции,
seed с явно тестовыми draft-товарами и фикстуры. Авторизация моделируется
`SET ROLE` + UUID claims, как контекст PostgreSQL; это не проверка JWT gateway.
Боевые данные, заказы и реальные пользователи не используются.

Проверены FK/unique/check, циклы категорий, скидки/stock, видимость по предкам,
публикация/архив, роли, запрет чтения заказов, защита роли, снимки и идемпотентный
ключ, SQL-политики фотографий и параметры bucket.

`private.reserve_inventory(jsonb)` — недоступный API owner-only примитив:
агрегирует дубликаты, упорядочивает варианты, атомарно обновляет остатки через
условный UPDATE, откатывает все изменения при недостатке. Он предназначен для
**единой будущей транзакции заказа**, а не отдельного вызова из браузера.
Проверены успешное списание/отказ/полный rollback/невалидный ввод. Конкурентные
сессии и полный checkout не проверены и не объявляются готовыми.

`npm run db:check` — только read-only smoke реального API с .env.local: доступ
публичных таблиц и запрет anon orders/order_items/admin RPC. Без env завершается
ошибкой. Не заменяет следующие обязательные hosted-проверки:

1. Применение/история миграций, schema cache API и повторный smoke.
2. Два настоящих Auth-пользователя: обычный и назначенный администратор;
   проверить каталог/роли/закрытые заказы через API под их JWT.
3. Временные тестовые изображения: admin upload/read/delete; обычный/anon upload
   запрещён; draft read запрещён, published read разрешён.
4. Storage API отклоняет SVG, подменённый MIME, неверный путь и файл > 5 МиБ.
5. Фактическое исполнение SQL на версии PostgreSQL тестового Supabase проекта.

Только после этого блок можно отметить done. Vercel Preview пока не получает
production Supabase env; CI запускает изолированные тесты без облачных ключей.
Проект Supabase для Production будет отдельным, подключается явно позже.
