## Работа владельца

`/admin/orders`: список обновляется при переходе/перезагрузке, есть «Оновити список».
Поиск — точный номер, фильтры — статус и включительные даты по Europe/Kyiv,
сортировка по времени/сумме, страницы по 20 заказов. Фильтры сохраняются в URL.
Контакты не включаются в URL, публичные логи или аналитику.

Карточка `/admin/orders/[id]` показывает контактные данные, ручную доставку Новой
почтой, комментарий и снимки order_items. Текущая цена/название/остатки каталога
не заменяют исторические значения заказа. Удалённый вариант не уничтожает снимок.

Выбрать новый статус → проверить текст → подтвердить. Разрешены:
- new → processing или cancelled;
- processing → shipped или cancelled;
- shipped → completed;
- completed и cancelled — конечные.

Отмену shipped/completed не реализуем как возврат: это отдельный будущий процесс
возвратов. Отменённый заказ не активируется без нового безопасного резервирования.
Оплата, API доставки, печать накладных и уведомления не добавлены.

## Транзакции и безопасность

Миграция `20261125000700_admin_orders.sql`:
- `admin_order_search` возвращает только данные списка после private.is_admin();
- `admin_order_status` независимо проверяет роль Auth UUID в private.admin_users;
- выполнение разрешено authenticated, но обычный пользователь получает 42501;
- прямые INSERT/UPDATE/DELETE orders/order_items запрещены authenticated;
- клиент использует существующую сессию и publishable key, новый privileged key
  для админки не нужен. Checkout secret нужен только для публичного тестового заказа;
- Next.js повторно проверяет пользователя и роль для каждого чтения/операции,
  точный Origin защищает POST от CSRF; тело ограничено 2 KiB;
- все admin ответы private/no-store/noindex, результат формы не содержит контактов.

Транзакция берёт guards дерева/каталога 52005001/52005002 в том же порядке,
что checkout и редактор товаров, затем блокирует заказ FOR UPDATE. Версия updated_at
монотонна с точностью PostgreSQL; устаревшая версия с другим целевым статусом
отклоняется 40001. Повтор текущего статуса — no-op независимо от старой версии.

При отмене количества суммируются по исходным variant_id/product_id, возвращаются
существующим вариантам и вместе со status=cancelled записывается inventory_released_at.
Любая ошибка откатывает весь возврат и статус. Архивные/переименованные варианты
сохраняют ID и получают свой остаток. Удалённые варианты не воссоздаются по SKU,
цвету или размеру: история сохраняется, UI предупреждает о необходимости сверки
склада. Это исключает ошибочный возврат похожему, но другому варианту.

## Проверки

`npm run lint`, `npm run typecheck`, `npm test`, `npm run build`.
`npm run orders:test:hosted -- --dev-only` требует локальный сервер на 3013.
Проверяются реальные параллельные транзакции, повтор отмены, конфликт версий,
снимки цены, поиск/фильтры, RLS, анонимный API и CSRF. Сценарий проверяет проект
kos-jeans-dev, использует только собственные фиктивные контакты/категорию/вариант.
Административные роли не назначаются: SQL тест проверяет уже подтверждённый UUID
владельца. Клиентский metadata не используется для роли.

После теста только собственные заказы отменяются, склад восстанавливается один раз,
тестовые товар/категория архивируются. История не удаляется, существующий ассортимент
не меняется. Принудительный teardown собственных shipped fixtures — доверенная
тестовая уборка владельцем БД, не доступный через админку переход статуса.
