## Подготовка владельцем

1. Открыть [Supabase Dashboard](https://supabase.com/dashboard/projects), выбрать свою
   организацию и проверить тариф/лимиты. Создать отдельный проект с именем `kos-jeans-prod`
   только после согласования. Не активировать платный compute, branching, PITR или иной add-on автоматически.
2. Регион выбрать с учётом региона Vercel Functions и аудитории Украины, доступности
   регионов и требований к данным. Близкие регионы уменьшают сетевые задержки;
   конкретный регион и допустимую стоимость согласовать перед созданием.
3. Сгенерировать уникальный пароль БД и сохранить в своём менеджере паролей вместе
   с данными аккаунта, email восстановления и резервными кодами MFA. Не сохранять пароль,
   secret key или access token в Git, чате, скриншотах, shell history или `.env.example`.
4. Дождаться Ready, проверить имя и Project Ref в Dashboard. Новый ref должен отличаться
   от dev. В Supabase надпись ветки `main PRODUCTION` бывает и у **dev-проекта**: решает
   имя/ref проекта, а не одна эта надпись.

## Создание схемы — вместе с Codex после отдельного разрешения

## Проверка прав и фотографий

После схемы проверить RLS на public/private таблицах и storage.objects, FK,
уникальность SKU/slug/variant, запрет отрицательного stock и точные денежные суммы.
Anon/обычный пользователь не меняют ассортимент и не читают заказы, admin RPC
требуют реальную роль. `private` не добавлять в Exposed schemas.

Bucket `store-media` остаётся **private**. Миграции задают JPEG/PNG/WebP и серверные
правила путей/ролей; bucket limit5MiB, интерфейс дополнительно ограничивает3MiB,
декодирует фото до32MP, удаляет EXIF и сохраняет WebP. Не переводить bucket в public
ради загрузки картинок. Фотографии выдаются после RLS и Storage access, private/no-store;
Next optimizer принимает только статические `/images/storefront/**`.

## Первый постоянный администратор

1. В новом проекте выключить публичную регистрацию. Authentication → Users → Add user:
   владелец создаёт **свою** учётную запись, email и пароль вводит самостоятельно.
2. Проверить подтверждение email и записать UUID именно этой записи. Dev UUID не переносится.
3. Подтвердить UUID владельцу перед назначением роли. Codex не назначает роль по догадке
   или user_metadata. SQL Editor открывается только в `kos-jeans-prod`.
4. После подтверждения выполнить отдельную транзакцию ниже. Подставлять только проверенный
   UUID; не сохранять заполненный SQL в публичном репозитории.

```sql
begin;
do $$
declare target uuid := 'ПРОВЕРЕННЫЙ-UUID-ИЗ-AUTH';
begin
  if not exists (
    select 1 from auth.users where id = target and email_confirmed_at is not null
  ) then raise exception 'Confirmed Auth identity required'; end if;
  if exists (select 1 from private.admin_users where user_id <> target)
    then raise exception 'Review existing administrators first'; end if;
  insert into private.admin_users(user_id) values (target) on conflict do nothing;
end $$;
commit;
```

Это шаблон; сейчас не выполнялся. Права дают только через private.admin_users,
не через metadata/cookie и не автоматически первому зарегистрировавшемуся.

## Резервное копирование и восстановление

Выбрать ответственного, допустимую потерю данных и время восстановления **до продаж**.
Для Free не считать автоматические ежедневные downloadable backups или PITR включёнными:
Supabase рекомендует регулярный CLI-export и хранение копий вне проекта. Free также
может приостанавливаться при низкой активности. Условия повторно проверить перед запуском.
[Backups](https://supabase.com/docs/guides/platform/backups),
[Free pausing](https://supabase.com/docs/guides/platform/free-project-pausing).

- Схема/миграции находятся в Git; резервные данные заказов/Auth — отдельно, зашифрованно,
  с ограниченным доступом. В Git/чат дампы не отправлять. Периодичность зависит от допустимой потери.
- Экспорт должен явно включать нужные роли, схему, данные и Auth-процедуру по актуальной
  инструкции. Один default `db dump` не объявлять полной резервной копией.
- Файлы **Storage не входят** в backup PostgreSQL: сохранять отдельные оригиналы/объекты,
  пути и метаданные, проверять возможность обратной загрузки в private bucket.
- Восстановление сначала репетировать в отдельном изолированном проекте: схема/Auth,
  данные/FK/суммы/stock, storage files/policies, назначенные администраторы. Не восстанавливать
  поверх действующего магазина без остановки заказов, плана и отдельного разрешения.
- Решение о платных автоматических backups/PITR/тарифе принимает владелец; сейчас расходы
  не включены. До успешной репетиции восстановления не считать резервирование готовым.
