# AGENTS.md — KOS JEANS

> Постоянные инструкции для Codex. Этот файл должен лежать **в корне локального Git-репозитория `kos-jeans`**. Читай его в начале каждой новой сессии и перед любыми изменениями проекта.

## 1. Миссия

Ты — ведущий full-stack разработчик, архитектор и UI/UX-инженер проекта **KOS JEANS** — интернет-магазина одежды для Украины.

Нужно постепенно создать **работающий коммерческий магазин**, а не только красивый макет. Сайт должен быть удобен покупателям, а владелец должен управлять ассортиментом без программирования.

**Основные принципы:**

- Язык интерфейса: **украинский**; техническая документация и общение с владельцем: **русский**. Позже возможен второй язык.
- Валюта: **гривна (₴)**.
- Главный ориентир по логике и структуре: **https://spazio.ua/**. Изучи доступные публичные страницы референса перед разработкой соответствующих разделов. Заимствуй только общие UX-паттерны: меню, категории, фильтры, карточку товара, корзину. **Не копируй** изображения, логотипы, тексты, код или узнаваемое оформление Spazio.
- Бренд: **KOS JEANS**. Стиль: современный минималистичный fashion e-commerce — белый, чёрный, графит, нейтральные цвета, сдержанные denim-акценты, качественные изображения и хорошая мобильная версия.
- Архитектура должна позволять подключить настоящий домен позже **без переписывания проекта**.

## 2. ОБЯЗАТЕЛЬНЫЙ ПРОТОКОЛ: РАБОТА СТРОГО ПО БЛОКАМ

**Самое важное правило: за одну пользовательскую команду выполняй только ОДИН блок из дорожной карты ниже.**

1. В начале работы изучи `AGENTS.md`, `PROJECT_PROGRESS.md` (если существует), структуру файлов, `git status` и состояние текущего блока.
2. Если прогресс ещё не заведён, создай `PROJECT_PROGRESS.md` со списком всех блоков, статусами (`todo / in_progress / done / blocked`), датами и ссылками. Файл должен храниться в репозитории.
3. **Начинай с первого незавершённого блока.** Если пользователь явно назвал другой блок, сначала проверь, выполнены ли его зависимости.
4. Выполни только задачи текущего блока. Не начинай следующий блок «заодно», даже если технически можешь.
5. Для каждого блока: изменения файлов → локальная проверка → короткий отчёт → фиксация прогресса. Не отмечай `done`, если критерии приёмки не пройдены.
6. **Остановись после блока** и жди явного сообщения владельца: **«Продолжай»**, **«Следующий блок»** или конкретного нового задания. Самостоятельно не переходи к следующему блоку.
7. Если внешний доступ, ключ, авторизация или разрешение отсутствуют, зафиксируй `blocked`, укажи **точное действие владельца** и остановись. Не подменяй недоступный функционал имитацией, выдавая его за готовый.
8. Если пользователь просит исправить уже выполненный блок, исправь его, проведи проверки, обнови прогресс и снова остановись.
9. Перед каждым опасным или необратимым действием (удаление данных, изменение production-базы, платежи, force push, расход средств) запрашивай разрешение. **Платные услуги не подключай самовольно.**
10. Пользователю не нужно повторно пересказывать весь план: достаточно подтвердить выполнение очередного блока.

**Команда запуска для Codex:** «Прочитай AGENTS.md и PROJECT_PROGRESS.md, выполни только первый незавершённый блок, проверь результат, обнови прогресс и остановись до моего подтверждения».

## 5. Функциональные требования: что строим

### 5.1. Публичный магазин

**Шапка:** логотип `KOS JEANS`, динамическое меню, поиск, корзина с количеством, мобильная навигация.

**Первоначальные разделы** (впоследствии редактируются администратором):

- **Жінкам:** Джинси, Штани, Куртки, Шорти, Футболки, Інший одяг.
- **Чоловікам:** Джинси, Штани, Куртки, Шорти, Футболки, Інший одяг.
- **Новинки**, **Розпродаж**, **Всі товари**.

Категории и подкатегории **хранятся в БД**, поддерживают вложенность, сортировку, скрытие, изменения URL и динамически появляются в меню и каталоге. Не зашивай структуру каталога в React.

**Главная:** hero-баннер и CTA «Переглянути колекцію», категории, новинки, популярное, коллекция джинсов, распродажа, информация о бренде, преимущества, контакты, footer. Товарные блоки получают реальные опубликованные товары из базы. Баннеры и настройки впоследствии управляются из админки.

**Каталог `/catalog` и категории:** карточки с фотографиями, ценой и старой ценой, бейджами, хлебные крошки, фильтры по категории, размеру, цвету, цене и наличию; поиск; сортировка по новизне, цене и — только при реальных данных — популярности; пагинация или «показать ещё». Состояние фильтров желательно отражать в URL. На мобильном — удобная панель фильтров. Человекочитаемые slug-адреса категорий.

**Страница товара:** фотогалерея, увеличенные изображения, название, SKU, цена, старая цена, выбор размера/цвета при наличии, остаток каждого варианта, описание, состав и характеристики, таблица размеров, доставка и возврат, похожие товары. Отсутствующий вариант нельзя купить.

**Корзина:** товар + конкретный вариант (размер/цвет), количество, цены, сумма, удаление, изменение количества, сохранение при перезагрузке. Проверка цены и доступности должна повторяться сервером при заказе.

**Оформление заказа без регистрации и онлайн-оплаты (v1):** имя, телефон, город, способ доставки, отделение/адрес и комментарий; первоначально данные «Нової пошти» вводятся вручную. Заказ сохраняется в БД, имеет номер, статусы и снимки названия/варианта/цены на момент покупки. Корректное уменьшение остатков через транзакцию и защита от дублирования запросов. Позже — интеграции Nova Poshta API и платёжного провайдера.

**Информационные страницы:** контакты, доставка и оплата, обмен и возврат, политика конфиденциальности, условия пользования. **Не выдумывай** реквизиты компании, адреса, юридические обещания и сроки; используй явно помеченные редактируемые шаблоны.

### 5.2. Админ-панель `/admin` — приоритетный функционал

Админка требует **защищённой авторизации и серверной проверки роли**, а не просто скрытого меню. Никакой публичной регистрации администратора.

Разделы: **Dashboard**, **Товари**, **Додати товар**, **Категорії**, **Замовлення**, **Банери**, **Налаштування магазину**.

**Добавление/редактирование товара:**

- Название, slug, артикул/SKU, описание, характеристики, материал, цвет.
- Категория/подкатегория из динамического дерева, возможность переназначить.
- Цена и старая цена в **UAH**, корректный денежный тип.
- Несколько фото в Supabase Storage: загрузить, посмотреть, назначить главную, переставить, удалить.
- Произвольные размеры: цифровые (26–36 и другие) и буквенные (XS–XXL и другие).
- **Отдельный остаток для каждого варианта**; при необходимости сочетание размер+цвет и отдельный SKU.
- Статусы `draft`, `published`, `archived`, флаги `new`/`featured`, а скидка отображается согласно данным.
- Поиск, фильтр, быстрое редактирование, архивирование и безопасное удаление.
- **Ключевой критерий:** создать категорию → добавить товар, фотографии, цену и размеры → опубликовать → товар сразу появляется в правильном разделе **без commit/push/deploy**. Изменения цены/остатка так же отражаются без обновления кода.

**Категории:** создание, переименование, картинка, описание, вложенность, порядок, скрытие и безопасное удаление/архивирование без потери товаров.

**Заказы:** номер, дата, имя, телефон, товары/варианты/количество, стоимость, доставка, статусы `new`, `processing`, `shipped`, `completed`, `cancelled`; изменение статуса и идемпотентное восстановление остатков при отмене.

**Настройки и баннеры:** адреса социальных сетей, контакты и промоблоки через визуальный интерфейс без изменения кода.

### 5.3. Структура данных

Минимум: `categories`, `products`, `product_categories` (если нужна множественная принадлежность), `product_images`, `product_variants`, `orders`, `order_items`, `store_settings`, `homepage_banners` и механизм admin roles.

Требования:

- Схема БД в миграциях (в репозитории), внешние ключи, индексы, ограничения и понятные имена.
- Вложенные категории через `parent_id` или эквивалентную модель.
- Уникальные/стабильные идентификаторы; URL-slug не должен быть единственным ключом данных.
- Цены — в целых копейках либо точном `numeric`, **без хранения денег в float**.
- Снимки покупки в `order_items` (цена, наименование, выбранный размер), чтобы история заказа не менялась при редактировании каталога.
- Проверки наличия/списания — **атомарная транзакция PostgreSQL**, исключающая overselling, с корректной защитой от повторного оформления.
- RLS на всех чувствительных таблицах; публичные пользователи читают только допустимый опубликованный каталог, не изменяют цены и не читают чужие заказы.
- Хранилище фото должно контролировать тип, размер, путь и права загрузки.

### 5.4. Безопасность и качество

- Вход администратора через Supabase Auth и серверную авторизацию ролей.
- Никогда не помещай service-role ключ или иные секреты в браузер; публичный anon/publishable key используй только по назначению с RLS.
- Валидация input на сервере, лимиты запросов на оформление заказов, защита от злоупотреблений.
- Запрет отрицательных остатков и покупок недоступных размеров.
- Личные данные покупателей — только там, где требуются, не логируй их публично.
- SEO: title/description, Open Graph, sitemap, robots, понятные URL, Product structured data там, где уместно.
- Скорость: оптимизированные изображения, корректный responsive layout, loading/empty/error states.
- Тестовые/preview окружения и тестовые заказы должны быть изолированы от production; preview не должен индексироваться.

## 8. Команды и критерии качества

Используй актуальные имена npm-скриптов из `package.json`. По возможности должны работать:

```bash
npm run lint
npm run typecheck
npm run build
npm test
```

Если тестов ещё нет — не имитируй успех `npm test`; вводи тесты по мере появления соответствующих функций. Каждая новая критическая серверная операция должна иметь проверку успешного и неуспешного сценария.

**Контрольный пользовательский сценарий к концу проекта:**

1. Войти в `/admin` как администратор.
2. Создать категорию «Джинсові куртки».
3. Добавить товар «Куртка Denim Blue», 3–5 фотографий, цену 1499 ₴ и размеры S/M/L с остатками.
4. Опубликовать и увидеть его в категории на сайте без изменения кода.
5. Изменить цену на 1299 ₴, размер M установить в 0 — изменения отражаются без Git push.
6. Как покупатель открыть товар, выбрать доступный размер, добавить в корзину, оформить тестовый заказ.
7. Увидеть заказ в `/admin`, изменить статус и проверить корректные остатки.
8. Изменить дизайн через Codex → commit/push → увидеть результат на Vercel; изменения базы при этом не требуют деплоя.
